API・DB設計書

ER図、テーブル概要、API一覧、解答判定・得点加算の初期設計を整理する資料です。

1. 位置づけ

本資料は、謎解き企画用アプリのER図・DB設計・API設計の初期案を定義する。要件定義・画面設計・システム設計をもとに、実装時のデータ構造とサーバー処理を具体化するための資料である。

3. テーブル概要

テーブル役割主な注意点
hosts出題者アカウントSupabase AuthのユーザーIDと対応させる。
rooms企画ルームroom_codeは参加者が入力する短いコード。重複を防ぐ。
participants参加者・チーム同一ルーム内で名前重複を禁止するか検討する。
questions問題情報answer_textは参加者に返さない。画像パスの公開範囲に注意。
answer_aliases別解・表記ゆれ正答候補を複数登録する場合に使う。
submissions提出ログ正解・不正解を問わず履歴を残す。
score_events得点加算ログ得点の二重加算防止のため、participant_id + question_id に一意制約を検討する。
room_events進行ログ誤操作やトラブル時の確認に使う。
hintsヒント公開前ヒントを参加者へ返さない。

4. データ制約・重要ルール

対象制約目的
rooms.room_code一意ルーム参加時の衝突を防ぐ。
participantsroom_id + name を一意にするか検討ランキング表示の混乱を避ける。
questionsroom_id + order_no を一意問題順序の重複を防ぐ。
score_eventsparticipant_id + question_id を一意同一問題での得点二重加算を防ぐ。
submissionssubmitted_textは保存するが、必要に応じて表示制限不適切入力や個人情報混入に備える。
得点の真実は score_events か submissions から再集計できる状態にする。participants.score_total だけに依存すると、障害時に復旧しづらい。

5. API設計方針

  • 参加者向けAPIと出題者向けAPIを明確に分ける。
  • 出題者向けAPIは認証・ルーム所有者チェックを必須にする。
  • 参加者向けAPIはparticipant_idとセッション情報を検証する。
  • 解答判定APIは正答文字列を返さず、結果と得点差分のみ返す。
  • 得点加算はDBトランザクション内で行う。

8. 主要リクエスト・レスポンス例

Request:

9. 解答正規化ルール

判定前に解答文字列を正規化する。どこまで許容するかは謎解きの難易度と演出に影響するため、問題ごとに設定可能にするのが望ましい。

処理初期方針例
前後空白除去必須「 こたえ 」→「こたえ」
全角/半角統一推奨ＡＢＣ → ABC
大文字/小文字統一英字問題では推奨Answer → answer
ひらがな/カタカナ統一問題ごとに検討カギ → かぎ
記号除去慎重に検討「あ・い」→「あい」は意図とズレる可能性あり

10. 得点加算のトランザクション方針

  1. 参加者セッションを検証する。
  2. 問題が解答受付中か確認する。
  3. 解答を正規化する。
  4. 正答・別解と照合する。
  5. submissionsに提出ログを保存する。
  6. 正解かつ未加点の場合のみscore_eventsを作成する。
  7. participants.score_totalを更新する、またはscore_eventsから再集計する。
  8. 結果のみを参加者へ返す。
score_eventsに一意制約を置くと、API連打や通信リトライ時にも二重加点を防ぎやすい。
