1. 文書の目的とスコープ

本文書は、謎解き企画用アプリの開発に向けて、企画・設計・実装の前提となる要件を整理するためのものである。 参加者側アプリ、出題者側アプリ、バックエンド、データ管理、セキュリティ、運用面を含め、初期開発で実装すべき範囲と、詳細設計で詰めるべき範囲を明確にする。

方針：要件定義では「何を実現するか」「なぜ必要か」「守るべき制約」を定める。API仕様、DBカラムの厳密な型、画面コンポーネントの詳細、実装コード構造は詳細設計で扱う。

2. アプリ概要

本アプリは、出題者が用意した問題画像を参加者に提示し、参加者がキーボードで解答を入力することで得点を獲得できる謎解き企画支援システムである。 参加者はWeb上でルーム番号を入力して参加し、出題者は問題登録、進行管理、解答状況確認、得点管理を行う。

参加者側アプリ

ルーム参加、問題画像閲覧、解答入力、正誤結果確認、得点確認を行う。

MVP必須スマホ対応PC対応

出題者側アプリ

ルーム作成、問題登録、画像アップロード、正答設定、問題提示、参加者・得点管理を行う。

MVP必須認証必須管理画面

3. 想定ユーザーと権限

ユーザー種別主な目的主な権限認証方針
参加者 企画に参加し、問題に解答する ルーム参加、問題閲覧、解答送信、自分の得点閲覧 ルーム番号＋参加者名またはチーム名。MVPではログイン不要でも可。
出題者 問題を準備し、企画を進行する ルーム作成、問題登録、問題切替、解答状況確認、得点操作 ログインまたは管理用パスコードを必須とする。
管理者 複数企画やシステム全体を管理する 全ルーム管理、ユーザー管理、データ削除、監査 初期MVPでは出題者と兼ねてもよい。

4. 利用フロー

4.1 参加者側の流れ

  1. 参加者がWebアプリにアクセスする。
  2. ルーム番号を入力する。
  3. 参加者名またはチーム名を入力する。
  4. ルームに参加する。
  5. 出題者が問題を開始するまで待機する。
  6. 問題画像を確認する。
  7. 解答欄にキーボードで解答を入力する。
  8. 送信ボタンまたはEnterキーで解答を送信する。
  9. サーバー側で正誤判定を行い、結果を受け取る。
  10. 正解の場合、得点が加算される。
  11. 次の問題または終了画面へ進む。

4.2 出題者側の流れ

  1. 出題者が管理画面にアクセスする。
  2. ログインまたは管理用パスコードで認証する。
  3. ルームを作成する。
  4. 問題画像、正答、配点、制限時間などを登録する。
  5. 参加者の参加状況を確認する。
  6. 問題を開始し、参加者画面へ提示する。
  7. 解答状況、正解者、得点を確認する。
  8. 必要に応じてヒント表示、締切、次問提示を行う。
  9. 企画終了後、最終結果を表示・出力する。

5. 参加者側アプリの画面要件

画面目的主な構成要素優先度
ルーム参加画面 参加者が企画ルームへ入る タイトル、ルーム番号入力、参加者名入力、参加ボタン、エラー表示 必須
待機画面 企画開始または次問開始まで待機する ルーム番号、参加者名、待機メッセージ、接続状態、参加人数 必須
問題解答画面 問題画像を見て解答する 問題番号、問題タイトル、問題画像、解答欄、送信ボタン、得点、残り時間 必須
解答結果表示 送信後の正誤・得点を確認する 正解/不正解、獲得点、再解答可否、締切表示 必須
得点確認画面 自分の得点・順位を確認する 合計点、順位、正解数、ランキング 準必須
終了画面 企画終了後の結果を確認する 終了メッセージ、最終得点、最終順位、ランキング 準必須

5.1 解答入力仕様

  • 解答はキーボードで入力できる。
  • Enterキーで送信できる。
  • 空文字は送信できない。
  • 前後の空白は除去する。
  • 大文字・小文字を区別するかは問題ごと、またはルームごとの設定とする。
  • ひらがな・カタカナ、全角・半角などの表記ゆれ対応は拡張機能として検討する。
  • 複数回解答の可否は問題ごとに設定できることが望ましい。

6. 出題者側アプリの画面要件

画面目的主な構成要素優先度
出題者ログイン画面 出題者のみ管理画面へ入れるようにする ログインフォーム、管理用パスコード入力、エラー表示 必須
ルーム管理画面 企画ルームを作成・選択・削除する ルーム一覧、新規作成ボタン、ルーム番号、開催状態、参加人数 必須
問題管理画面 問題を登録・編集する 問題一覧、画像アップロード、正答、別解、配点、制限時間、公開状態 必須
ルーム進行画面 企画中に問題提示や締切を操作する 現在の問題、開始ボタン、締切ボタン、次問ボタン、ヒント表示、終了ボタン 必須
参加者管理画面 参加者の参加状況を確認する 参加者一覧、接続状態、得点、正解数、強制退出、名前修正 準必須
解答状況画面 参加者の解答をリアルタイムに確認する 解答ログ、正誤、送信時刻、参加者名、問題別フィルタ 準必須
ランキング画面 得点順位を確認・表示する 順位表、合計点、正解数、最終結果表示、公開用表示モード 準必須
結果出力画面 終了後に結果を保存・共有する CSV出力、解答ログ出力、ランキング出力 後回し

6.1 出題者側の重要操作

問題登録

  • 画像アップロード
  • 正答・別解登録
  • 配点設定
  • 制限時間設定

進行管理

  • 問題開始
  • 解答受付停止
  • 次問へ移動
  • 企画終了

監視・修正

  • 参加者状態確認
  • 解答ログ確認
  • 得点調整
  • 不具合時の手動対応

6.2 出題者画面で必要な警告・確認

  • 問題を開始すると参加者側に表示されるため、開始前に確認ダイアログを出す。
  • 解答受付を締め切ると参加者は送信できなくなるため、締切前に確認する。
  • 正答や配点を企画中に変更する場合、既存の得点への影響を明示する。
  • ルーム削除や問題削除は取り消し困難な操作として扱う。

7.3 共通機能

  • 入力値のバリデーションを行う。
  • 通信エラー時にユーザーへ状況を表示する。
  • 企画状態の変化を参加者画面に反映する。
  • 重要操作や解答送信はサーバー側で処理する。
  • 問題の正答データは参加者側に送信しない。

8. バックエンド・システム要件

本アプリでは、正答判定、得点加算、ルーム状態管理、画像管理をサーバー側で行う必要がある。特に謎解き企画では、正答データの秘匿が重要であるため、フロントエンドのみで完結する実装は避ける。

参加者ブラウザ ─┐ ├─ Webフロントエンド / サーバー処理 ─ データベース 出題者ブラウザ ─┘ │ ├─ 画像ストレージ └─ リアルタイム通知基盤

8.1 サーバー側で扱うべき処理

処理理由備考
解答判定正答を参加者側に漏らさないため正答・別解・表記ゆれ処理をサーバー側に置く。
得点加算参加者による改ざんを防ぐため二重加点防止が必要。
問題状態管理開始・締切・終了状態を一元管理するため参加者側は現在状態を購読・取得する。
画像アップロード問題画像を安全に保管・配信するため出題者のみアップロード可能。
出題者認証管理画面の不正操作を防ぐためMVPでも最低限必要。
ログ保存トラブル対応や結果確認のため送信時刻・解答内容・判定結果を保存する。

8.2 リアルタイム性

出題者が問題を開始・締切・次問へ移動した際、参加者画面に速やかに反映されることが望ましい。MVPでは数秒以内の反映を目標とし、必要に応じてリアルタイム購読または短間隔ポーリングを採用する。

  • 問題開始時：参加者画面が待機画面から問題画面へ遷移する。
  • 問題締切時：解答欄を無効化し、受付終了を表示する。
  • ランキング更新時：必要に応じて参加者・出題者画面に反映する。

8.3 想定APIカテゴリ

要件定義段階ではエンドポイント名やリクエスト形式までは確定しないが、以下の処理カテゴリを想定する。

カテゴリ主な処理
Roomルーム作成、ルーム取得、状態更新、参加受付制御
Participant参加者登録、再接続、参加者一覧取得
Question問題作成、編集、画像登録、出題順管理
Submission解答送信、正誤判定、解答ログ取得
Score得点取得、ランキング取得、手動補正
Auth出題者ログイン、権限確認

10. 技術スタック方針

結論：要件定義書には、技術スタックの「候補・方針・制約」は盛り込むべき。ただし、ライブラリの細かな構成、API設計、DB物理設計、ディレクトリ構成は詳細設計で分離するのがよい。

10.1 推奨構成

領域推奨技術理由代替候補
フロントエンド Next.js + React + TypeScript 参加者画面と出題者画面を同一プロジェクトで作りやすく、サーバー側処理も統合しやすい。 React + Vite
UI Tailwind CSS または CSS Modules 短期間でレスポンシブUIを作りやすい。 Material UI, shadcn/ui
バックエンド Next.js Server Functions / Route Handlers 解答判定や得点加算をサーバー側に置ける。MVPでは構成がシンプル。 Node.js + Express, Hono, NestJS
データベース Supabase PostgreSQL ルーム、問題、解答、得点のような関係データを扱いやすい。 Firebase Firestore
画像ストレージ Supabase Storage 問題画像のアップロード・保管・アクセス制御をまとめやすい。 Firebase Cloud Storage, S3
リアルタイム通知 Supabase Realtime またはポーリング 問題開始や締切などの状態変化を参加者画面へ反映できる。 WebSocket, Firebase Realtime/Firestore listener
認証 Supabase Auth または簡易管理パスコード 出題者画面の保護が必要。MVPでは簡易方式、正式版では認証基盤を推奨。 NextAuth/Auth.js, Firebase Authentication
ホスティング Vercel Next.jsとの相性がよく、MVP公開が容易。 Cloudflare Pages, Firebase App Hosting

10.2 MVPにおける現実的な構成案

Next.js アプリ ├─ /participant : 参加者画面 ├─ /host : 出題者画面 ├─ Server Functions / API Routes │ ├─ ルーム作成 │ ├─ 解答判定 │ ├─ 得点加算 │ └─ 進行状態更新 └─ Supabase ├─ PostgreSQL : ルーム・問題・参加者・解答・得点 ├─ Storage : 問題画像 ├─ Auth : 出題者認証 └─ Realtime : 問題状態・ランキング更新

10.3 Firebase構成を選ぶ場合

Firebaseでも、Firestore、Cloud Storage、Authentication、Cloud Functionsを組み合わせれば実現可能である。リアルタイム更新を扱いやすい一方、得点や問題・解答の関係を複雑に集計する場合は、データ構造を慎重に設計する必要がある。

10.4 技術選定の判断

重視すること向いている構成
SQLで問題・参加者・得点を整理したいNext.js + Supabase
リアルタイム更新を最速で試したいFirebase または Supabase Realtime
自分でバックエンドを細かく作りたいNext.js + Node.js API + PostgreSQL
短期間でMVPを公開したいNext.js + Supabase + Vercel

11. 非機能要件

分類要件目安
対応端末PC、スマートフォン、タブレットで利用できる。レスポンシブ対応
対応ブラウザChrome、Safari、Edgeで利用できる。最新版を主対象
操作性参加者が迷わず解答できる。主要操作は1〜2クリック以内
表示性能問題画像が大きく遅延せず表示される。画像圧縮・適切なサイズ管理
応答性能解答送信後、結果が速やかに返る。通常時1〜2秒以内を目標
同時接続小規模イベントの参加者に対応できる。MVPでは20〜100人程度を想定
可用性一時的な通信断から復帰できる。再接続・再読み込み対応
保守性問題追加やルール変更に対応しやすい。問題データと判定ロジックを分離
運用性当日のトラブルに運営が対応できる。手動得点修正・ログ確認

12. セキュリティ要件

最重要：正答データを参加者側のHTML、JavaScript、APIレスポンスに含めない。解答判定は必ずサーバー側で行う。

12.1 必須対策

  • 出題者画面には認証を設ける。
  • 正答、別解、配点操作は出題者権限のみ可能にする。
  • 参加者側に正答データを送信しない。
  • 解答判定と得点加算はサーバー側で実行する。
  • 同一問題での二重加点を防止する。
  • ルーム番号は推測されにくい桁数・形式にする。
  • 画像アップロードはファイル種別・サイズを制限する。
  • 出題者の重要操作はログに残す。

12.2 追加で検討する対策

  • 参加者ごとにセッションIDを発行する。
  • 短時間に大量送信する参加者を制限する。
  • ルーム参加に合言葉を追加する。
  • 企画終了後、問題画像や解答データを一定期間で削除する。
  • 公開ランキングに表示する名前の扱いを事前に明示する。

13. MVP範囲

13.1 初期開発で必ず作るもの

  • 参加者のルーム参加
  • 参加者名またはチーム名登録
  • 出題者ログイン
  • ルーム作成
  • 問題画像アップロード
  • 正答・配点登録
  • 出題者による問題開始・締切・次問操作
  • 参加者側への問題画像表示
  • 解答送信
  • サーバー側正誤判定
  • 得点加算
  • 現在得点表示

13.2 後回しにしてよいもの

  • CSV出力
  • 複雑なランキング演出
  • ヒントの段階表示
  • 表記ゆれの高度な吸収
  • 複数ルームの高度な管理
  • 参加者の強制退出
  • 詳細な監査ログ画面
  • 公開用大型スクリーン表示

13.3 MVP成功条件

  • 出題者が問題を登録し、参加者に提示できる。
  • 参加者がルームに入り、問題画像を見て解答できる。
  • 正答判定がサーバー側で行われる。
  • 正解時に得点が加算される。
  • 企画中に出題者が進行を止めずに操作できる。

14. 要件定義と詳細設計の分離

技術やシステム構成は要件定義にも含めるべきだが、粒度を分ける必要がある。本アプリでは、以下のように分離する。

要件定義に含める詳細設計に回す
参加者・出題者が何をできるか 画面コンポーネントの具体的な分割
正答判定をサーバー側で行う方針 判定関数の実装、正規化処理の詳細
ルーム、問題、参加者、解答、得点が必要という概念 DBテーブル名、カラム名、型、インデックス、制約
