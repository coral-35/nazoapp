# Supabase連携済み通信アプリのルーム取得・作成API 500エラー調査と修正

## 背景

謎解き問題出題用の通信アプリを作成している。

現在、Supabaseのセッティングは完了しており、管理者ログインは実際に成功するところまで確認済み。

しかし、管理者ログイン後に以下の操作を行うと、サーバー側で `500 Internal Server Error` が返ってくる。

- ルーム情報の取得
- ルームの作成

ログインまでは成功しているため、Supabase Authの基本設定は大きくは間違っていない可能性が高い。  
一方で、ルーム関連API、Supabaseクライアント、DBスキーマ、RLSポリシー、環境変数、APIルート実装のいずれかに問題がある可能性がある。

---

## 目的

ルーム情報取得・ルーム作成時に発生している `500` エラーの原因を突き止め、修正可能であれば修正まで完了させる。

単に推測で直すのではなく、以下を行うこと。

1. 500エラーの発生箇所を特定する
2. サーバーログ・例外内容・レスポンス内容を確認する
3. Supabase関連の設定・クエリ・RLS・テーブル定義を確認する
4. 原因を説明できる状態にする
5. 修正を実装する
6. 実際にルーム取得・ルーム作成が成功するところまで確認する

---

## 対象機能

少なくとも以下を確認すること。

### 1. ルーム情報取得

該当するAPI、関数、ページ、フックなどを探して確認する。

例：

- `/api/rooms`
- `GET /rooms`
- `fetchRooms`
- `getRooms`
- `loadRooms`
- `rooms` テーブルへの `select`
- 管理画面でルーム一覧を取得する処理

実際のプロジェクト構成に合わせて、該当箇所を特定すること。

### 2. ルーム作成

該当するAPI、関数、ページ、フックなどを探して確認する。

例：

- `/api/rooms`
- `POST /rooms`
- `createRoom`
- `insertRoom`
- `rooms` テーブルへの `insert`
- 管理画面で新規ルームを作成する処理

実際のプロジェクト構成に合わせて、該当箇所を特定すること。

---

## 調査方針

以下の順で調査すること。

### 1. まず現状を再現する

アプリを起動し、可能なら以下を確認する。

- 管理者ログインが成功するか
- ルーム一覧取得時に500が出るか
- ルーム作成時に500が出るか
- ブラウザのNetworkタブ相当で、どのAPIが500を返しているか
- サーバーコンソールにどのような例外が出ているか

もし手元環境で再現できない場合は、その理由を明記する。

### 2. 500を返している箇所を特定する

以下を確認する。

- API Route / Server Action / Route Handler / Backend endpoint
- Supabase query の直後で例外が発生していないか
- `catch` 節で詳細ログを握りつぶしていないか
- `console.error(error)` などで十分なエラー情報が出ているか
- レスポンスが常に500になっていないか

必要に応じて、一時的に安全な範囲でログを追加して原因を確認する。

ただし、アクセストークン、JWT、service role key、DBパスワードなどの秘密情報はログに出さないこと。

### 3. Supabase接続設定を確認する

以下を確認する。

- Supabase URL
- anon key
- service role key を使うべき箇所と使ってはいけない箇所
- server-side client と client-side client の使い分け
- 環境変数名の不一致
- `.env.local` などが読み込まれているか
- `NEXT_PUBLIC_` が必要な変数と不要な変数の切り分け

注意：

- secret key をフロントエンドに露出しないこと
- `.env` や `.env.local` をコミット対象にしないこと
- 既存の秘密情報を表示・出力しないこと

### 4. DBスキーマを確認する

ルーム関連のテーブルについて、以下を確認する。

- `rooms` テーブルが存在するか
- カラム名がコードと一致しているか
- 必須カラムに値を入れているか
- `created_at` などのデフォルト値が必要なカラムに設定されているか
- `id` の型がコードと一致しているか
- `uuid` / `text` / `int` の不一致がないか
- 外部キー制約に違反していないか
- insert時に不要な値を渡していないか

もしマイグレーションファイルやSQLファイルが存在する場合は、それも確認すること。

### 5. RLSポリシーを確認する

Supabaseでは、ログインできていても、RLSの設定によって `select` や `insert` が失敗する可能性がある。

以下を確認する。

- `rooms` テーブルでRLSが有効か
- `select` ポリシーが存在するか
- `insert` ポリシーが存在するか
- 管理者ユーザーに対して許可されているか
- `auth.uid()` とアプリ側のadmin判定が一致しているか
- `admins` / `profiles` / `users` などの管理者判定テーブルがある場合、参照条件が正しいか
- API側でservice role clientを使うべきか、ユーザーのJWTを使うべきか

RLSが原因と考えられる場合は、最小限の安全なポリシー修正案を提示・実装すること。

ただし、すべてのユーザーに無制限の `select` / `insert` を許可するような雑な修正は避けること。

---

## 修正方針

修正では、以下を優先する。

1. 原因を確認してから直す
2. 既存のログイン機能を壊さない
3. セキュリティを下げすぎない
4. RLSを無効化するだけの安易な修正を避ける
5. ルーム取得・作成の両方が成功することを確認する
6. エラー時には原因が追えるようなログやレスポンスに改善する

---

## 具体的に確認してほしい観点

以下を重点的に確認すること。

### API実装

- `GET` と `POST` の分岐が正しいか
- request body の読み取りが正しいか
- JSON parse エラーが起きていないか
- required field のバリデーションがあるか
- Supabase query のエラーを適切に扱っているか
- `throw` された例外が500として返っていないか
- レスポンス形式がフロントエンド側の期待と一致しているか

### フロントエンド

- APIのURLが正しいか
- HTTP method が正しいか
- request body が正しいか
- `Content-Type: application/json` が必要な箇所で設定されているか
- ログイン後のセッション・トークンがAPIに渡っているか
- エラー表示が不十分な場合、最低限の表示改善ができるか

### Supabase

- `select` でエラーが返っていないか
- `insert` でエラーが返っていないか
- `.single()` / `.maybeSingle()` の使い方が適切か
- 存在しない行に対して `.single()` を使って例外扱いになっていないか
- カラム名の typo がないか
- RLSによる `permission denied` が起きていないか
- `relation does not exist` / `column does not exist` が起きていないか

---

## 必要な権限・情報が不足している場合

必要な権限や情報が不足している場合は、推測で進めず、毎回具体的に求めること。

その際は、以下の形式でユーザーに依頼すること。

```text
作業を進めるには、以下が必要です。

必要なもの:
- ...

必要な理由:
- ...

秘密情報の扱い:
- ...
```

求める可能性があるものの例：

- Supabase Dashboard のSQL Editorへのアクセス
- SupabaseのTable Editorで `rooms` テーブルを確認する権限
- Supabase Logsの確認結果
- `.env.local` の変数名一覧
- 実際の値ではなく、設定されている環境変数名
- 500発生時のサーバーログ
- 該当APIのレスポンス本文
- `rooms` テーブルのスキーマ
- RLSポリシー定義
- マイグレーションSQL

注意：

- service role key、JWT、DBパスワードなどの秘密情報をチャットに直接貼るよう求めないこと
- 必要な場合は、ローカル環境の `.env.local` に設定してもらう形にすること
- 秘密情報をログや画面に表示しないこと

---

## 破壊的操作に関する制約

以下の操作を行う場合は、事前にユーザーへ確認すること。

- 既存テーブルの削除
- 既存カラムの削除
- 本番データの削除
- RLSの全面無効化
- 全ユーザーに広く権限を開放するポリシー変更
- service role key を使う設計への大きな変更
- 認証・認可設計の大幅変更

軽微なコード修正、ログ追加、バリデーション追加、明らかなtypo修正、ローカル検証用の非破壊的変更は進めてよい。

## 完了条件

以下を満たすまで作業すること。

1. 管理者ログイン後、ルーム情報を取得できる
2. 管理者ログイン後、ルームを作成できる
3. 500エラーの原因が説明できる
4. 修正内容がコードまたはSQLとして反映されている
5. 既存の管理者ログイン機能が壊れていない
6. 秘密情報がログ・ソースコード・コミット対象に混入していない
7. 必要な権限や情報が足りない場合は、具体的にユーザーへ確認している

---

## 作業の進め方

時間がかかっても構わないので、修正できるところまで粘り強く調査・修正すること。

ただし、情報不足や権限不足で進められない場合は、曖昧に止まらず、必要な情報を具体的に列挙してユーザーに確認すること。

推測で大きな変更を入れないこと。  
特に認証・認可・RLSまわりは、安全性を維持したまま最小限の修正にすること。
