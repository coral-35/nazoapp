## 2. アプリの目的

謎解き企画に用いるWebアプリを実装します。

アプリは大きく以下の2つで構成します。

- 参加者側アプリ
- 出題者側アプリ

参加者は、ネット上でルーム番号と名前を入力してルームに参加し、出題者が提示した問題画像を見て、キーボードで解答を入力します。  
解答が出題者の準備した正答と一致していれば得点が加算されます。

出題者は、ルーム作成、問題登録、画像アップロード、正答登録、配点登録、問題開始、解答締切、得点確認を行います。

## 4. 技術スタック

原則として以下を使ってください。

- Next.js App Router
- TypeScript
- React
- Supabase
  - Postgres
  - Auth
  - Storage
- Vercelデプロイを想定
- CSS Modules、通常のCSS、またはTailwind CSSのいずれか

既存プロジェクトがすでに存在する場合は、その構成を尊重してください。  
未作成の場合は、Next.js + TypeScript を前提に新規構築してください。

---

## 5. 絶対に守るセキュリティ制約

以下は必ず守ってください。

- 正答判定は必ずサーバー側で行う
- 正答文字列を参加者側に送らない
- 正答文字列を参加者側HTML、JavaScript、APIレスポンスに含めない
- `SUPABASE_SERVICE_ROLE_KEY` をクライアントコードに含めない
- `SUPABASE_SERVICE_ROLE_KEY` に `NEXT_PUBLIC_` を付けない
- 参加者から送られた得点値を信用しない
- 得点はサーバー側で計算する
- 同一参加者・同一問題の二重得点をDB制約またはトランザクション相当の処理で防ぐ
- 未認証ユーザーが出題者APIを実行できないようにする
- 参加者が他ルームの問題や得点を不正に参照できないようにする

## 6. DB設計方針

資料内のAPI・DB設計書を優先してください。  
不足がある場合は、以下のようなテーブル構成を採用してください。

### `rooms`

- `id`
- `room_code`
- `title`
- `status`
- `current_question_id`
- `created_by`
- `created_at`
- `updated_at`

### `participants`

- `id`
- `room_id`
- `name`
- `token`
- `total_score`
- `created_at`
- `updated_at`

### `questions`

- `id`
- `room_id`
- `title`
- `image_url`
- `answer_text`
- `normalized_answer`
- `points`
- `order_index`
- `status`
- `created_at`
- `updated_at`

### `submissions`

- `id`
- `room_id`
- `participant_id`
- `question_id`
- `submitted_answer`
- `normalized_submitted_answer`
- `is_correct`
- `awarded_points`
- `created_at`

必要に応じて補助テーブルを追加して構いません。

重要制約:

- `room_code` は一意
- 同一ルーム内で参加者名は重複しないことが望ましい
- `participant_id + question_id` の正解得点は一度だけ
- 正答文字列は参加者側から直接取得できないようにする

SupabaseのRLSを使う場合は、認証済み出題者と匿名参加者の権限を明確に分けてください。  
RLSをMVPで厳密に組み切れない場合でも、少なくともNext.jsのサーバー側APIでアクセス制御してください。

## 7. API設計方針

資料内のAPI設計を優先してください。  
不足がある場合は、以下のAPIを実装してください。

### 7.1 参加者向けAPI

#### `POST /api/join-room`

- ルーム番号と参加者名で参加
- participant情報または復帰用tokenを返す

#### `GET /api/current-question`

- `room_code` と participant token から現在問題を取得
- 正答は絶対に返さない

#### `POST /api/submit-answer`

- participant token、question_id、answer を受け取る
- サーバー側で正誤判定
- 正解なら得点加算
- 二重加算を防ぐ
- 結果のみ返す

#### `GET /api/my-score`

- 自分の得点を取得

### 7.2 出題者向けAPI

- `POST /api/admin/create-room`
- `POST /api/admin/create-question`
- `POST /api/admin/upload-question-image`
- `POST /api/admin/start-question`
- `POST /api/admin/close-question`
- `GET /api/admin/rooms`
- `GET /api/admin/rooms/[roomId]`
- `GET /api/admin/scores`

出題者向けAPIは必ず認証チェックしてください。

## 12. 完成条件

以下をすべて満たすまで作業してください。

### 12.1 参加者側

- 存在するルーム番号で参加できる
- 存在しないルーム番号ではエラーになる
- 参加者名未入力ではエラーになる
- 出題者が開始した問題画像が表示される
- 解答を入力して送信できる
- 正答なら正解表示になる
- 誤答なら不正解表示になる
- 正解時のみ得点が加算される
- 同じ問題で再度正答しても得点が二重加算されない
- 締切後は解答できない
- 自分の現在得点が表示される

### 12.2 出題者側

- ログインできる
- 未ログインでは管理画面に入れない
- ルームを作成できる
- ルーム番号を確認できる
- 問題画像をアップロードできる
- 正答と配点を登録できる
- 問題を開始できる
- 問題を締め切れる
- 参加者一覧を確認できる
- 得点一覧を確認できる

### 12.3 セキュリティ

- 参加者側レスポンスに正答が含まれない
- ブラウザにservice role keyが露出しない
- 出題者APIは未認証では実行できない
- 参加者が任意の得点を送って改ざんできない
- 得点の二重加算が起きない

### 12.4 実行

- `npm install` が成功する
- `npm run dev` でローカル起動できる
- `npm run build` が成功する
- 必要な環境変数が `.env.example` に整理されている
- READMEにセットアップ手順が書かれている

## 14. 注意

このMVPでは、派手な演出よりも以下を優先してください。

1. 正答が漏れない
2. 得点が壊れない
3. 出題者が本番で操作できる
4. 参加者がスマホで迷わず解答できる
5. ローカルと本番で再現可能に動く

ランキング、ヒント、QRコード、演出アニメーション、詳細分析はMVP対象外です。  
ただし、実装上の拡張性を損なわない構造にしてください。
