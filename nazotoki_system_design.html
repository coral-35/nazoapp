システム設計書

技術選定、バックエンド責務、セキュリティ、リアルタイム通信、MVP範囲を整理する資料です。

1. 位置づけ

本資料は、謎解き企画用アプリを実現するためのシステム構成・技術選定・バックエンド方針・運用方針を定義する。詳細なAPI仕様やテーブル定義は「API・DB設計書」に分離する。

要件定義と詳細設計の分離: 本資料では「なぜその構成にするか」「どの責務をどこに置くか」までを扱い、具体的なエンドポイント名・カラム定義・コード構成は詳細設計で扱う。

2. システム上の重要要件

重要度要件理由
必須正答データを参加者側へ送らないブラウザの開発者ツールから答えが見える事故を防ぐため。
必須解答判定と得点加算はサーバー側で行う不正な得点操作や二重加算を防ぐため。
必須出題者側は認証必須問題切替・締切・得点操作などの管理機能を保護するため。
推奨問題状態はリアルタイムに反映するイベント中の操作体験を滑らかにするため。
推奨再接続・ページ更新から復帰できる当日の通信トラブルを軽減するため。

3.1 MVP推奨構成

領域推奨技術採用理由
フロントエンドNext.js / React / TypeScript参加者側と出題者側を同じ技術で実装でき、サーバー側処理も扱いやすい。
ホスティングVercelNext.jsとの相性が良く、MVPを素早く公開しやすい。
DBSupabase PostgreSQLルーム・参加者・問題・解答・得点をリレーショナルに管理しやすい。
認証Supabase Auth出題者ログインを簡単に実装できる。
画像保存Supabase Storage問題画像を管理し、公開/非公開の扱いを設計しやすい。
リアルタイムSupabase Realtime または WebSocket問題開始・締切・得点更新を即時反映しやすい。
MVPでは、Next.js + Supabase + Vercel の構成が最も実装速度と管理しやすさのバランスが良い。

4. 責務分担

処理実行場所理由
問題画像の表示フロントエンド参加者に見せるため。ただし画像URLの扱いには注意する。
解答入力フロントエンドUI操作として入力を受け付ける。
解答判定サーバー側正答を隠し、不正判定を防ぐため。
得点加算サーバー側 + DBトランザクション二重加算を防ぎ、一貫性を守るため。
問題切替出題者画面 + サーバー側権限確認が必要な操作のため。
ランキング集計DBまたはサーバー側全参加者の得点を一貫して集計するため。

5. ルーム状態管理

イベント進行は、ルームの状態を中心に管理する。参加者側画面はルーム状態を購読し、自動的に表示を切り替える。

状態意味参加者側表示出題者側操作
draft準備中参加不可または準備中表示問題登録、設定変更
waiting参加受付中待機画面参加者確認、開始
question_open解答受付中問題解答画面締切、ヒント公開
question_closed解答締切結果・待機画面次問へ、集計確認
finished企画終了終了画面ランキング確認、CSV出力

6. セキュリティ・不正対策方針

最重要: 正答文字列・正答判定ロジック・得点加算条件を参加者側JavaScriptに含めない。
リスク対策
参加者が正答を覗く正答はDBに保存し、参加者側には送らない。判定APIは結果のみ返す。
解答APIを連打する同一問題・同一参加者の正解得点は一度だけ加算する。必要に応じてレート制限を設ける。
他チームになりすます参加時にparticipant_idとセッションを発行し、以後の送信に使う。
出題者画面を不正操作する出題者認証とルーム所有者チェックを必須にする。
画像URLから未公開問題を見る画像の公開範囲、署名付きURL、出題タイミングでのURL発行を検討する。

7. リアルタイム通信方針

次のイベントはリアルタイム反映の対象とする。

  • ルーム状態変更: waiting → question_open → question_closed → finished
  • 現在問題の変更
  • ヒント公開
  • 参加者数・解答数・ランキングの更新
リアルタイム通信が不安定な環境に備え、参加者側は一定間隔で現在状態を再取得できるようにする。リアルタイム一本足打法はイベント当日に怖い。

9. MVP範囲

9.1 MVPで必ず作る

  • ルーム作成
  • 参加者のルーム参加
  • 問題画像の登録と表示
  • 解答送信
  • サーバー側の正誤判定
  • 得点加算
  • 出題者による問題開始・締切

9.2 MVP後に追加する

  • ヒント機能
  • ランキング公開制御
  • CSV出力
  • 表記ゆれ対応
  • 複数ルーム同時運用
  • 詳細な監査ログ
